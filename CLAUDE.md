# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é este repositório

Um PWA de arquivo único, sem build, para a frota de empurradores da Navecunha (Grupo VDA):

| Pasta | Conteúdo |
|---|---|
| `manutencao/` | **SMF** · Sistema de Manutenção da Frota (NP Navecunha 055: Anexo I, OMs preventivas/corretivas, óleo, cronograma, indicadores). Quase todo trabalho é em `manutencao/index.html` |
| `manutencao/servidor/` | Cópia versionada do servidor Google Apps Script do SMF (ver o README da pasta) |
| `docs/` | Documentos normativos de origem (NP 055, Anexo I visual, FR 049_B, Matriz técnica) em HTML/DOCX. Linkados pela Biblioteca do SMF (`../docs/...`) — não mover nem renomear. `Como_a_frota_trabalha.html` = resumo de uma folha do ciclo da manutenção para reuniões (na Biblioteca do enxuto). `Manual_Operacao_SMF.html` = manual de operação (caderno A4 com fluxogramas e mapa mental em SVG); ao mudar tela, fluxo ou regra, atualize o capítulo correspondente |
| `index.html` (raiz) | Só redireciona para `manutencao/` |

O antigo CTLE_LUB (Controle de Lubrificação, que ficava na raiz) foi um teste, está descontinuado e foi removido; seu módulo foi absorvido pelo SMF. Menções a “CTLE_LUB” no código do SMF são só históricas.

O SMF fala com o deployment Apps Script em `NUVEM_PADRAO` (topo de `manutencao/index.html`). A fonte da verdade do servidor é o editor do Apps Script; mudanças de contrato (ações, campos) exigem atualizar os dois lados e a cópia em `manutencao/servidor/`.

## Comandos

Não há build, lint, testes nem gerenciador de pacotes. Publicação: GitHub Pages da `main` (https://arlesson2025.github.io/NAVECUNHA/manutencao/).

- Rodar: servir a raiz do repositório por HTTP (ex.: `python -m http.server 8765 --bind 127.0.0.1`) e abrir `/manutencao/`. O app só registra o service worker em `https:`; o comportamento offline real se testa no celular, pelo GitHub Pages. Ao mudar arquivos pré-cacheados, confira que todos baixam (`caches.open(...).addAll(ARQ)` no console).
- Dados de exemplo: o app gera uma frota simulada (`gerarExemplo` / `carregarExemplo`); o banner “Dados de exemplo” aparece enquanto existirem `js/81-dados-de-exemplo-completos.js` (`exemploDemo`, uma vez por aparelho, registro `ex-demo-v1`) completa para apresentação: onde está cada empurrador (`S.cfg.situExemplo`, desfeito em `limparExemplo`), docagens com estaleiro e custo, laudos anteriores (tendência), OM em conferência, OMs para anexar no Sankhya (`skDemo`, o `skPend` ignora seed sem essa marca), avaria em viagem, prestadores e treinamentos.
- **Teste das telas** (compara o estilo em ordem alfabética das propriedades): `python testes/telas.py` (precisa de playwright + Chromium) abre a versão desta pasta e a da `main` com a mesma data e os mesmos dados de exemplo e compara o HTML de cada tela, o estilo calculado de cada elemento (pega mudança de CSS), os Anexos II gerados e o código final de `VX`/`AFTER`. Os arquivos vêm direto do disco pelo Playwright (sem servidor HTTP). Rode antes de cada push; numa limpeza tem de dar tudo IGUAL. Saída em `testes/saida/` (fora do git).
- Servidor: o código é colado manualmente no editor do Apps Script e implantado como App da Web; a URL `/exec` vai em Administração → Nuvem.

## Como ler o código do SMF (`manutencao/js/*.js`, ~1 MB em 79 arquivos)

**Desde 24/10/2026 o código não fica mais no `index.html`** (que tem só a estrutura da página, ~8 KB): cada antigo bloco `<script>` virou um arquivo em `manutencao/js/NN-assunto.js`, carregado por `<script src>` **na mesma ordem** (o número NN é a ordem), cada um com o seu `'use strict'`; o CSS principal está em `manutencao/css/smf.css`. Para achar algo, Grep em `manutencao/js/`; o núcleo é `js/02-nucleo.js`. Os arquivos grandes (núcleo ~300 KB) também não se leem inteiros: Grep e Read com `offset`/`limit`. Arquivo novo: crie `js/NN-nome.js` e ponha o `<script src>` no `index.html` na posição certa (o service worker pega a lista do próprio `index.html`). Nomes de topo continuam num escopo global só (todos os arquivos), e os números de linha citados abaixo são do antigo arquivo único: localize pelos marcadores.

- Topo (~linha 22): `NUVEM_PADRAO` e `carregarLibsPdf()`. As bibliotecas de PDF (html2canvas, jsPDF) ficam em `manutencao/lib/` e só carregam quando `gerarPDF`, `lubMakePdf` ou `apPdf` são chamadas; não edite os `.min.js`.
- CSS principal: `manutencao/css/smf.css` (o resto do CSS é injetado pelos blocos em JS).
- `LOGOS` aponta para `img/logo-nav.png` e `img/logo-vda.png` (antes eram base64 dentro do arquivo); estão em `ESSENCIAIS` no `sw.js`.
- **Anexo I (`A1`) fica em `manutencao/dados/anexo1.js`**, um item por linha, carregado por `<script src>` logo antes do núcleo (precisa estar disponível de forma síncrona: dezenas de blocos usam `A1` na carga). Para consultar um item, Grep em `dados/anexo1.js` por `"id":"1\.1\.1"`. Ao editar, mantenha cada linha um objeto JSON válido.
- Formulários oficiais FR 049_B, FR 027_L e FR 016_E ficam em `manutencao/forms/`, carregados por `lubFormTxt()` e postos no iframe via `srcdoc`. O FR 049_B recebe trocas de texto exatas em `lubAbrirForm` — se editar o formulário, mantenha esses trechos idênticos. `.gitattributes` (`-text`) guarda esses arquivos byte a byte (LF); não reformate nem converta quebras de linha.
- No PowerShell, leia com `-Encoding UTF8`; sem isso os acentos saem corrompidos.

### Núcleo (bloco `<script>` que começa em `const LOGOS`, até antes de “LUBRIFICAÇÃO · módulo”)

- **Dados de domínio**: `A1` (itens do plano — Anexo I; `A1M` indexado por id), `EQN` (equipamentos), `FROTA_MATRIZ`/`FROTA_PADRAO` (cadastro dos empurradores CJA…), `CLASSES` (criticidade corretiva), `ETAPAS_P`/`ETAPAS_C` (fluxo das OMs).
- **Utilidades**: `$`, `$$`, `esc` (sempre escapar ao montar HTML), `nf`, `pD`/`isoD`/`brD` (datas locais ao meio-dia), `uid`, `toast`, `modal`.
- **`recs(kind)` tem cache por tipo** (`RECS_C`), invalidado quando o Map `S.recs` muda (`set`/`delete`/`clear` contam versão em `S.recs.__v`). Mudar `kind` ou `excluido` de um registro só vale depois de `saveRec` (que faz `S.recs.set`). Foi isso que levou as telas de 6–8 s para ~0,3 s.
- **Armazenamento**: IndexedDB `ctle_man` (stores `recs` e `kv`), com fallback em memória (`MEM`). Estado global em `S` (`recs` Map, `cfg` compartilhada, `session`, `pending`, `pdfPend`).
- **Gravação/sincronização**: `saveRec(r)` → grava local, põe o id em `S.pending`, agenda `syncNow()`. `syncNow` faz *push* da fila e depois `list` desde `lastSync`; `cfg` remota vence se `cfgAt` for mais novo. `api(action, body)` faz POST `text/plain` para `S.url` (evita preflight CORS do Apps Script).
- **Perfis**: `can.edit()` (logado) e `can.admin()` (`role === 'admin'` = Supervisor; `op` = Analista; `opr` = Operador, bloco “Perfil Operador”: vê só “Chegada e saída”, abre o FR 027_L, informa OM dos NO; senha definida pelo Supervisor em Administração; servidor v11 só aceita dele `fr027`, `hor`, `horp`, `saida` e corretiva nova). A situação no porto/em viagem também é recalculada dos registros (`situRecalc`: FR 027_L e saída mais recentes), porque a configuração compartilhada (`setConfig`) só o Supervisor grava.
- **Roteamento**: hash `#view/arg` → `route()` → `render()`. `render()` escolhe a função da view no mapa base **mesclado com `VX`**, escreve `#main.innerHTML`, e chama `AFTER[view]()` para ligar eventos. Eventos são delegados em `#main.onclick/onchange` via atributos `data-*`.

### Camadas de patch (blocos `<script>` de “LUBRIFICAÇÃO · módulo”, ~linha 3170, até o fim)

O app cresceu empilhando ~50 blocos, cada um com um cabeçalho `/* ===== … ===== */` descrevendo a mudança. **Blocos posteriores sobrescrevem os anteriores**, por estes padrões:

- `VX.<view> = novaFuncao` — troca a tela.
- Envolver handlers: `{ const a0 = AFTER.x; AFTER.x = () => { a0(); const m = $('#main'), c0 = m.onclick; m.onclick = e => { …; return c0 && c0(e); }; }; }`
- Envolver views: `{ const v0 = vHor; vHor = function () { const h = v0(); … }; }`, inclusive injetando HTML via `indexOf` no HTML de outra view.
- Menu: quem vence é o bloco “Menu por decisão” (último `<script>` do arquivo), que remonta `SECOES` **na ordem do trabalho**. Nomes atuais (bloco “Menu profissional”, aprovado em 22/10/2026, vence os anteriores): grupo **Operação** = **1 · Frota** (nº de empurradores em `.nav-ct`) → **2 · Programar preventiva** (seção `prev2`, view `emitir`) → **3 · Executar e lançar** (seção `omsv2`, view `oms`) → **4 · Conferir e encerrar** (seção `conf2`, view `omconf`, com o cartão “Anexar no Sankhya”); grupo **Gestão** (`cfg: true`) = Plano preventivo, Condição dos equipamentos, Indicadores, Biblioteca, Administração. Um ícone por item (`ICO`). As seções são **Frota N Empurradores** (seção `hoje`; o número vem de `S.cfg.frota.length` e embaixo, em letra pequena, “Diário & Viagens” via `s.sub`; nomes definidos pelo Supervisor em 21/10/2026 — o menu já não diz “Hoje”, então textos de tela dizem “na Frota”) (rotina + Situação da frota + alertas P1/P2 de compressão e de óleo) · **Plano preventivo** (seção `crono`, antes “Cronograma”; abas **Cronograma preventivo** = view `cxr` e **Anexo I** = view `matriz`, que saiu de Administração) · **OMs (Sankhya)** (seção `omsv2`) · **Condição** (Óleo da frota — com as Trocas lançadas no fim da mesma tela; `#lubreg` redireciona para lá —, Análise de óleo = view `anoleo` (matriz do laudo, tendência, programa de amostragem, limites `LAUDO_P`), Compressão do MCP, Calibração e docagem = view `controle`) · Indicadores (só KPIs e riscos) · Biblioteca · Administração. Ele parte das seções do splice do bloco “SMF v2” e da seção `compr` do bloco “Compressão do MCP”. **Mas as abas de uma seção ainda podem ser redefinidas depois** por `SECOES.find(x => x.id === '<seção>')` — ex.: as abas do Cronograma vêm da linha ~7245, não do splice. Antes de mexer em abas, procure a última ocorrência de `SECOES.find(x => x.id === '<seção>')` e confira no navegador (`nav.abas`).
- CSS adicional injetado via `<style>` criado em JS ou no fim do arquivo.

- **Nomes globais**: `const`/`let` de topo de todos os blocos dividem o mesmo escopo global. Redeclarar um nome que já existe em outro bloco (ex.: `LAY`, usado pelos painéis organizáveis) derruba o bloco inteiro com SyntaxError — e compilar o bloco isolado não acusa. Antes de criar um nome de topo, faça Grep por `(const|let|function)\s+NOME\b` no arquivo todo.
- **Janelas livres** (arrastar, redimensionar, minimizar, tela cheia): `janelasLivres(ws, chaveLocalStorage, seletorDoBotaoReorganizar)` no bloco "Compressão do MCP"; usada pela Compressão (`.cm-ws`), pelo Cronograma e pelo Óleo da frota (bloco “Óleo da frota no padrão do painel”, que usa `o3Dados()` do bloco v3 para os dados). Telas novas seguem esse padrão: `.vh` com `h1` + `p` e botões, blocos `.card` com `h2`, filtros em `.cm-chips`, cores `var(--badt/--warnt/--okt)` — sem shadow DOM nem fontes próprias. Para usar numa tela nova: envolver os cartões em `<div class="cm-v"><div class="cm-ws">…</div></div>` e chamar a função no `AFTER` da tela. O segundo filho de cada cartão vira alça de arrastar: elemento clicável dentro dele que não seja botão/link/campo (ex.: barra de gráfico em SVG) precisa de `data-nodrag` (ou `.rm-hit`), senão o clique se perde.

- **Antes de publicar**, confira a sintaxe de todos os arquivos com um parser de verdade (acorn): `node -e "const fs=require('fs'),a=require('acorn');for(const f of fs.readdirSync('manutencao/js'))try{a.parse(fs.readFileSync('manutencao/js/'+f,'utf8'),{ecmaVersion:'latest',allowReturnOutsideFunction:true})}catch(e){console.log(f,e.message)}"` não pode imprimir nada (um erro derruba o arquivo inteiro em silêncio, e os seguintes quebram com “X is not defined”; `new Function` não acusa chave aberta). Nunca ponha `// comentário` no meio de uma linha que continua com código — e isso **não** é pego pela checagem de sintaxe quando o resto da linha era declaração (o código fica válido e quebra só ao rodar). Por isso rode também o **teste de fumaça**: logado, abrir cada tela (`rotina, cxr, crono, audit, oms, emitir, oleo, anoleo, parmcp, compr, controle, kpi, falhas, bib, terc, trein, pecas, matriz, admin, hor`, uma `#omg/…` e uma `#om/…`, e `rotina` com `role: 'opr'`) chamando `render()` e escutando `error`/`unhandledrejection`; tem de dar zero erros.

Consequência prática: para saber o que realmente aparece numa tela, procure a **última** atribuição (`VX\.crono\s*=`, `AFTER\.crono\s*=`) — a primeira definição pode estar morta. Ao alterar, prefira editar o bloco que hoje vence; se acrescentar um novo bloco de patch, siga o mesmo formato de cabeçalho e coloque-o no fim.
